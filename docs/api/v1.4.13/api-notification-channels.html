Notification Channels

Engineer or admin CRUD for notification channels. Channels define how alert notifications are delivered (e.g., webhook, email, Slack).

Create Notification Channel

POST /api/v1/notifications/channels

Request body:

{
  "name": "Slack Ops",
  "channel_type": "slack",
  "config": {
    "webhook_url": "https://hooks.slack.com/services/...",
    "channel": "#network-alerts"
  },
  "enabled": true
}

Validation:

  • name and channel_type are required; channel_type must be one of webhook, email, slack, teams, in_app (400 otherwise, on create and update)
  • enabled defaults to true if omitted; explicit false creates the channel disabled (note: there is no toggle endpoint for channels — re-enable via PUT)
  • config defaults to {} if omitted
  • Webhook config.headers (custom HTTP request headers) is a JSON object of header name → value, e.g. {"Authorization": "Bearer …"}. A JSON-encoded string of such an object is accepted and stored as the object — older clients, including the web form before 2026-11-17, sent that shape, and delivery skipped it without a word. Names must be RFC 9110 tokens; values must be strings (numbers and booleans are kept as text) without CR, LF or NUL. Two names that differ only in case (Authorization and authorization) are one HTTP header, so such a pair is refused too. Anything else is a 400 naming the offending header or pair. An empty value removes the headers. Rows stored in the string shape still deliver their headers.

Secrets: password, Slack/Teams webhook_url and every custom header value are encrypted at rest when the installation has an encryption key (OSPREY_ENCRYPTION_KEY, which the Debian installer generates; without one they are stored in plain text, like the SNMP credentials), and returned as "***" by every endpoint (header names stay visible). A PUT that sends "***" back for one of them keeps the stored value — the edit form sends the config it received, so a rename no longer overwrites the secrets with the mask. A masked header with no stored header of that name (compared case-insensitively) is a 400: there is nothing to keep. Stored headers that are not a JSON object (possible only for a channel saved by an older client) are returned as a single "***" and are not sent with notifications; sending "***" back keeps them as stored, any other value replaces them.

Response: 201 Created

{
  "id": "uuid",
  "name": "Slack Ops",
  "channel_type": "slack",
  "config": {
    "webhook_url": "https://hooks.slack.com/services/...",
    "channel": "#network-alerts"
  },
  "enabled": true,
  "created_by": "uuid",
  "created_at": "2026-02-17T12:00:00Z",
  "updated_at": "2026-02-17T12:00:00Z"
}

Error responses:

  • 400 Bad Request -- Missing required fields or invalid request body
  • 403 Forbidden -- Non-admin user

Update Notification Channel

PUT /api/v1/notifications/channels/{channelID}

Partial update of a notification channel. Uses read-merge-write -- only fields present in the request body are updated; other fields are preserved. A present config replaces the stored config, except that a secret sent back as "***" keeps its stored value (see Secrets above), and headers is validated and canonicalised as on create.

Request body (all fields optional):

{
  "name": "Updated Channel Name",
  "channel_type": "webhook",
  "config": {"url": "https://example.com/webhook", "headers": {"Authorization": "***", "X-Tenant": "ops"}},
  "enabled": false
}

Response: 200 OK (updated notification channel object, secrets masked)

Error responses:

  • 400 Bad Request -- Invalid request body, invalid headers, or a masked header with no stored value
  • 403 Forbidden -- Non-admin user
  • 404 Not Found -- Channel does not exist

Delete Notification Channel

DELETE /api/v1/notifications/channels/{channelID}

Delete a notification channel.

Response: 204 No Content

Error responses:

  • 403 Forbidden -- Non-admin user
  • 500 Internal Server Error -- Database error

Test Notification Channel

POST /api/v1/notifications/channels/{channelID}/test

Send a test notification through the specified channel. Validates that the channel exists and its configuration is reachable.

The test uses the same transport rules as real alert delivery, so a passing test means delivery would succeed:

  • Webhook, Slack, Teams — the connection is refused at dial time when the host resolves to a private or internal address (DNS-rebinding safe, the same client alert delivery uses). Redirects are not followed. A webhook test sends the channel's custom headers exactly as alert delivery does (both stored shapes); a stored headers value that cannot be read fails the test with the reason — delivery itself then sends without the headers and logs a warning. So does a stored pair of names that differ only in case (saved before the API refused one): delivery sends the value of the later name in byte order every time and logs a warning.
  • Email — STARTTLS is used whenever the relay offers it. With "tls": true in the channel config (the UI default) it is required: a relay that does not advertise STARTTLS fails the test before any envelope or message data is sent. Port 465 with "tls": true uses implicit TLS. The whole SMTP conversation is bounded to 60 seconds.

Response: 200 OK

{
  "status": "ok",
  "message": "test notification would be sent"
}

Error responses:

  • 403 Forbidden -- Non-admin user
  • 404 Not Found -- Channel does not exist
