SAML 2.0 Sign-In Flow

GET  /api/v1/auth/saml/{providerID}/start
POST /api/v1/auth/saml/{providerID}/acs
GET  /api/v1/auth/saml/{providerID}/metadata

Rate limit: 30 requests per minute per IP (burst 10). SP-initiated only — IdP-initiated responses (no InResponseTo) are refused.

start builds a signed AuthnRequest, stores its ID in a signed relay cookie (osprey_saml_state, typ-bound, HttpOnly, SameSite=None; Secure — the ACS is a cross-site POST), and redirects to the IdP. acs verifies the assertion signature (a signed Response or Assertion of more than 1000 XML elements is refused — a fixed limit of the signature library), an AudienceRestriction naming this SP, a bearer SubjectConfirmation and an AuthnStatement (an assertion without any of them is refused, as is an encrypted assertion whose key is not wrapped with RSA-OAEP), expiry (±3 min clock skew) and that InResponseTo matches our request ID; then it JIT-provisions/links the user (NameID as the immutable subject, group attribute → role mapping) and issues the session, redirecting to /. Because the NameID is the subject, the AuthnRequest's NameIDPolicy and the SP metadata ask for the unspecified format (urn:oasis:names:tc:SAML:1.1:nameid-format:unspecified, sent in full because some IdPs refuse a policy without a Format): the IdP sends the identifier it is configured with, which must be stable — persistent, an email address or a username, never transient. Before 2026-11-17 Osprey asked for a transient NameID, which Microsoft Entra ID honours with a fresh random value at every sign-in; the second sign-in then met the account the first had created and failed with link_required. metadata returns the SP metadata XML to register at the IdP; the SP signing keypair is generated and persisted on first use (no openssl needed). Failures redirect to /?auth_error=<code> (invalid_state, sso_failed, provider_error), never rendering assertion detail.

The ACS URL and metadata URL both derive from auth.external_url.
